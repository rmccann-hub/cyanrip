*What this build's testing does not cover, and what running it found anyway.
Written so the gaps are testable rather than discoverable.*

**Subject:** `0.9.4-rc2+platterpus.11`, commit `1ffd1f6` (audit ran read-only at
`0707d61`; the three commits since are this audit's own record).
**Occasion:** the maintainer supplied an ISTQB-shaped test taxonomy and audit
spec (test levels / types / design techniques / process practices, phases 0–10
plus a gap checklist) and asked for it to be applied here.

- A **black-box sweep** (`tools/blackbox.py`, new at `be2ea24`) — 838 probes over

  an adversarial pass. **A subagent's report is a claim about artifacts, not an

## 1. Verified here, by hand

### 1.1 `docs/seam-commands.md` §7 is stale, and both projects have hash-agreed on the stale bytes

§7 is the generated boundary table and the **only** place the accepted argument
ranges are published; `--help` prints defaults, not ranges.

Line 504 publishes `-p '99=drop'` as **accepted, exit 0**. The binary at HEAD:

    $ cyanrip -d basic.cue -N -A -U -I -p '99=drop'
    Invalid track number 99 for pregap, list has 2 tracks!      exit 1
    $ cyanrip -d basic.cue -N -A -U -I -p '1=drop'              exit 0   (control discriminates)

The file last moved at `b9a9c53` (2026-08-07); the bound moved at `bf8ab3a`
(2026-08-15, *"Bound `-p` against the disc, not against a fixed 197"*). So it has
been wrong for eight days of commits.

Its `sha256` is byte-identical to the `seam-commands=` value in
`HANDSHAKE-SHARED-HASHES` at `round-15-lap-12.md:23`, so `tools/seam-check.py`
reports `OK`.

> **A shared hash proves both sides hold the same bytes. It can never prove the
> bytes describe the binary.** §7 has no `--check` and no gate, so it is the one
> shared artifact where those two facts can diverge silently — and they have.

**This is the one finding that cannot be fixed unilaterally.** `seam-commands.md`
is jointly owned; correcting a cell is a shared-file edit and needs a joint
version bump. It belongs in a lap. See §4.

### 1.3 Three live defects in the AccurateRip response parser

On a path **no dynamic control in this tree can reach**: `rip()` at
`tests/rip_images.py:88` hardcodes `-N -A -U`, so all 40 scenarios are offline by
construction, and `tools/sanitize-run.py` re-runs those same scenarios.

    src/accurip.c:66   rctx->data = av_realloc(...)          no NULL check
    src/accurip.c:67   memcpy(rctx->data + rctx->size, ...)  → memcpy(NULL + n)
    src/accurip.c:156  strcmp(content_type, ...)             CURLE_OK yields NULL
                                                             when no header is sent
    src/accurip.c:158  strstr((const char *)rctx.data, ...)  buffer built by raw
                                                             memcpy, never NUL-terminated

`src/coverart.c:129-131` — the sibling receive callback — **does** check its
realloc. **Two receive callbacks in one program that disagree is the signature of
a path nobody exercises.**

These bytes decide the `AccurateRip:` verdict the consumer parses as an archival
claim, and the path is live: every rig invocation passes `-N` but not `-A`.

### 1.4 `fun512.c:72` is signed-overflow UB on a directory

    long int len = ftell(f);
    if (len <= 0 || !(data = av_mallocz(len + 1))) {

Measured, not reasoned: `fopen(".")` succeeds and `ftell` returns exactly
`LONG_MAX`. So `len <= 0` is false and `len + 1` overflows **before any bound
check**. UBSan: `signed integer overflow: 9223372036854775807 + 1`.

The release build recovers — `Couldn't read "."!`, exit 5 — only because the
wrapped value makes `av_mallocz` fail. It survives *through* the undefined
behaviour, which is not the same as being correct.

Reached by `cyanrip -Y .` — a directory where a file is expected. `fun512` is the
checksum that guards the archival record.

### 1.5 Two bare `return 1;` skip the context teardown, and it closes the drive

`cyanrip_main.c:2184` and `:2186` are the `cyanrip_log_init()` and
`cyanrip_cue_init()` failure paths. They bypass `end:` entirely, so
`cyanrip_ctx_end()` at `:2673` never runs. **All 24 `goto end` sites reach it
correctly** — the file's own comment audits those, and a bare `return` is
invisible to that framing.

Measured: ~12.8 MB leaks from one root (the ctx at `:2026`, dragging
`cdio_paranoia_init`'s 11.3 MB). A leak at exit in a short-lived CLI is minor.
**The teardown is not only a free**: it also calls
`cdio_cddap_close_no_free_cdio()` and `cdio_destroy()`.

> So the failure paths on which the archival record **could not be opened** are
> exactly the ones that never close the drive.

Hardware consequence: `unknown (no drive in this environment)`.

### 1.6 The suite corrupted its own machine-readable record — FIXED

`tools/check-settled.py` **is** a registered meson test (`Settled facts`). Two
`docs/SETTLED.md` rows added earlier the same session carried the check cell
`meson test -C build consumer_argv`, so the suite re-entered meson on the **same**
build directory. Meson's log base is `<builddir>/meson-logs/testlog` with no
uniquifier: the inner run truncated the file the outer run was still appending to.

    before   567,612 bytes   151,418 NUL (26.7%)   47 of 61 records
    after    567,633 bytes             0 NUL       61 of 61 records

The JUnit copy was intact both times, because it is rewritten whole at `finish()`
rather than appended — which is why nothing noticed.

**The suite really had passed. Its machine-readable record of having passed was
corrupt**, and that is the artifact a CI job archives as proof a commit was green.
Fixed at `8e1fd20`; both cells now invoke the scenario the way meson does, and
`check-settled.py` refuses any cell re-entering `meson test` without `--logbase`.
Revert-proved on the guard alone.

**This defect was ours and was made during this session.** It is recorded at the
same weight as the others.

### 1.7 From the black-box sweep — two upstream defects, and one positive result

**Invalid UTF-8 truncates a name at the bad byte; a leading bad byte empties it.**
`av_utf8_decode` fails in `naming.c` and expansion stops: `START<bad>TAIL` names a
directory `START`; `<bad>TAIL` names nothing. With a **multi-component** folder
scheme an empty leading component makes the whole path **absolute** — with the
consumer's own `-D {album_artist}/{album}`, a full rip landed in **`/Some Album`**,
exit 0, nothing in the working directory. An explicitly empty `album_artist=` is
**refused with exit 1**, so a guard against an empty component exists and this
evades it.

**A logfile's first line is not always the fork banner.** With invalid UTF-8 in a
naming-scheme *argument*, the parse error goes through `cyanrip_log()` before the
header, so the log opens `Error parsing string: ...!`. `PROJECT_FORK_ID` is our
answer to "is this the fork?", and a consumer reading line 1 gets an error string.
`-Y` returns 0 on such a log. *(Metadata does not trigger this — the scheme is
expanded earlier. The first draft of this row said it did; a second run disproved
it.)*

**Positive result, stated because an absence of a finding is worth recording:**
metadata **cannot** escape the output directory. `/` is replaced by U+2215 before
it reaches the filesystem, and **16 of 16** traversal attempts — four hostile
values across all four `-T` modes — stayed contained.

## 2. Refuted by measurement

Filed so nobody re-derives them.

**A truncated backing `.bin` does NOT produce a false claim.** A lane flagged
`exit 0` / `Ripping errors: 0` / `Rip completed: yes` with zero-byte tracks as a
possible rank-3 finding. Both shapes are correct: a `.bin` short enough that a
later track *starts within it* is read as a **shorter disc** and reported
accurately (`Total time: 00:04.50` for 350 sectors, both tracks carrying real
audio); a `.bin` so short that a track's start is **past EOF** is refused with
`Unable to open device!` at column 0 and exit 1.

> A grep of that second output for `error|fail|warn` finds **nothing**, and nearly
> produced a phantom "silent non-zero exit" here. The message contains none of
> those words. Reading the artifact instead of the match count is the only reason
> it was caught.

**The truncated-NRG "18-exabyte allocation" is not ours.** ASan aborts on the
request; the shipping build prints `libcdio error: Requested count exceeds maximum
allowed value.` and exits 1. libcdio's own guard catches it — ASan simply aborts
earlier than that guard. Correctly-handled malformed input.

## 4. What needs the consumer's agreement

Only **§1.1**. `docs/seam-commands.md` is jointly owned by both projects; a cell
correction is a shared-file edit and takes a joint version bump, so it goes in a
lap rather than a commit. The proposed remedy — add `--check` to
`tools/probe-argv-surface.py`, regenerate §7 between explicit delimiters and diff,
exit non-zero on drift — is **ours to build and theirs to assent to**, and the
delimiters matter because the check must not claim prose the other side wrote.

Everything else in §1 is ours alone. **Five of the six are frozen by S-15** while
round 15 is open, and none makes the reviewed pin unsafe: they are next-round
work, per the rule that a finding defaults to the next round and promoting one to
blocking requires naming what it breaks in the artifact under review.
