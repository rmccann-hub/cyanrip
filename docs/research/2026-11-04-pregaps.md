# Pregap detection in established rippers

Research for the fork's `subchannel-pregap-varies` question: on a Pioneer BDR-209D, track 9 of the
reference disc reads 94 frames, 95 frames, or "94 or 95 (undecided)", and the undecided sector is
LSN 145567 (track 9's `INDEX 01` is LSN 145662). Written 2026-11-04. Nothing here ran on a drive,
and no downloaded code was executed.

Each finding carries one label:

- **[doc]**: a specification, a project's own documentation, or a pull request's description by
  its author.
- **[code]**: read in source at the commit named in "Sources read".
- **[forum]**: a forum post, mailing-list message or issue comment. Not verified.
- **[inference]**: my reading of code or documents. Not run.

Upstream cyanrip references below carry URLs for sourcing. Per the fork's `CLAUDE.md`, write
"upstream pull request 153" in a commit or pull request, never the `owner/repo#N` form or its URL.

## The answer

No established tool claims its pregaps are exact, and no public database can check one.
AccurateRip, CTDB, MusicBrainz and gnudb key on `INDEX 01` offsets only. With gaps appended to the
previous track, a pregap's length changes no checksum. EAC's own page says the deviance "should be
lower than 2-3 sectors". The tools that read the sub-channel most carefully are cdrdao's
default scan, redumper, DiscImageCreator and upstream's open pull request 153. They read raw P-W
sub-channel (READ CD selection `001b`) where the drive allows it, not formatted Q (`010b`).
cdrdao and pull request 153 place each frame by its own absolute address; redumper corrects a
shift it measures across the disc. All but pull request 153 read runs of consecutive sectors.
redumper and pull request 153 also cross-check a boundary against a neighbor, a second read or
the P channel. Our search reads formatted Q one sector per command and moves a bound on a single
frame.

Two documented mechanisms are consistent with track 9's record:

- In formatted-Q mode, "some drives silently return the previous sector's frame, with a valid
  CRC, in place of a damaged one". On pull request 153's test drive, that "made pregaps come out a
  frame short and vary between rips".
- A mode-2 (MCN) or mode-3 (ISRC) Q frame names no track or index. If one sits on the first pregap
  sector, the tools split. cdrdao, XLD, pull request 153 and our search give it to the previous
  track, one frame short. CUETools gives it to the next track. redumper settles it with the P
  channel.

Which mechanism holds at LSN 145567, if either, is not established. The cheapest observation that
could settle it is a raw P-W read of LSN 145560 to 145575 on the rig. EAC's 94 on a BDR-209D is
not an independent check: it reads through the same drive firmware.

## 1. EAC

**What it reads.** EAC is closed source, so only its author's words and its documentation say.

- [forum] EAC's author, Andre Wiethoff, on the EAC mailing list, 1999 (EAC 0.85 beta 4, when the
  methods were numbered 1 to 3): "Method 1 will read the Q-Subcodes with a specific read command,
  but this does not work for all drives...Method 2 will just seek the Q-Subcodes, method 3 will
  audio play the positions and retrieve by that the Q-Subcodes..."
  (groups.io, "Detecting Pre-Track Gap on Track 3", message 728).
- [inference] Read with cdrdao's and CUETools' code, the three match three known techniques.
  Method 1 (now A) matches READ CD with sub-channel. Method 2 (B) matches a seek or read, then
  READ SUB-CHANNEL (`42h`), as CUETools' fallback does. Method 3 (C) matches PLAY AUDIO, then READ
  SUB-CHANNEL, as cdrdao's binary search does. Not established: whether A to C still map to 1 to 3
  in current EAC, and which READ CD sub-channel value A requests.
- [doc] EAC's documentation (`eacdoc.pdf`, 2000, "Gap Technology"): "EAC has to search for the
  position a track ends ... because these pre-track gaps are found out by testing positions, it
  could occur that not 100% exact values are calculated, but in most cases it will be correct."
- [doc] exactaudiocopy.de, "Gap Technology": "it is possible that it will not be 100% accurate.
  But in most cases it will be correct, the deviance should be lower than 2-3 sectors."

**Accurate and secure.**

- [doc] Hydrogenaudio Knowledgebase, "EAC Drive Options" (written for EAC 0.99 prebeta 5): "EAC
  offers three methods: A, B, and C; the difference between them is unknown." Detection accuracy
  "affects how many times the gap info is read. Inaccurate is one read ... Accurate and Secure
  are multiple reads". Also: "There is no way to know if the values are 100% correct."
- [forum] An undated EAC setup guide (roozster.info): "The Detection accuracy is the number of
  times EAC counterchecks the detected gaps ... the Accurate and Secure modes retrieve the gaps
  several times to verify the gap positions."
- Not established: how many reads Accurate and Secure take, and what EAC does when they disagree.

**Known accuracy problems by drive.** All of these are forum reports.

- [forum] Hydrogenaudio topic 54163 (2007, Pioneer DVR-110D): "If there's a non-zero gap,
  cdrdao's value is less than EAC's by exactly 1 frame". One disc agreed exactly. Methods A, B and
  C in secure mode gave the same results.
- [forum] Hydrogenaudio topic 32516 (2005): PlexTools cue sheets were "about a frame off" from
  EAC's. On a gapless mix CD, methods B and C in secure mode gave a 1-frame gap on every track,
  and A in secure mode gave none.
- [forum] A 2010 blog test (Plextor PX-755SA and PX-760A, LG GDR8164B, in Chinese): A with Secure
  gave the same gaps on all three drives and at every speed tried. B with Secure differed between
  drives and speeds. C was unusable.
- [forum] EAC mailing list, 1999 (PlexWriter 8/20): only Inaccurate worked; Accurate and Secure
  hung the detection.
- Ours: EAC's rip of the reference disc on a BDR-209D gives track 9 as 94 frames
  (`docs/KNOWN-ISSUES.md`). It is the same drive model and possibly the same READ CD path, so it
  is not independent of the drive's behavior.

## 2. How other rippers find `INDEX 00`

### Comparison

| Tool | Search | Sub-channel read | Reads per sector | Frame failing its CRC | Frame of another sector | Mode-2/3 frame on the boundary |
|---|---|---|---|---|---|---|
| cdrdao `read-toc`, default | Linear scan of the whole track | READ CD `001b` raw P-W if probed, else `010b` | 1; resends only on a SCSI error | Skipped and counted | Placed by its own address | To the previous track [inference] |
| cdrdao, option `0x20` or `plextor` driver | Binary search | PLAY AUDIO 1 block, then READ SUB-CHANNEL | 1 or 2 per step | Not visible | Not detectable | Not handled |
| whipper, morituri | Run `cdrdao read-toc` | As cdrdao | As cdrdao | As cdrdao | As cdrdao | As cdrdao |
| XLD | Linear scan from 4 s before the track | macOS `DKIOCCDREAD`, user data plus Q | 1; up to 5 re-reads of the chunk | Skipped after 5 tries, sector still counted | Not detected; counted where read | To the previous track [inference] |
| CUETools (CUERipper) | Binary search on 5-sector windows | READ CD `010b`, no main channel; else READ + `42h` | 1 per window | Skipped; zero CRC accepted | Placed by its own address | To the next track [inference] |
| dBpoweramp | Not documented | Not established | Not established | Not established | Not established | Not established |
| cyanrip upstream `master` | None for a drive | None | None | None | None | None |
| Upstream pull request 153 (open) | Bounds, backtrack, walk; second read confirms | `001b` if a 10-sector probe passes, else `010b` | Up to 5, 100 per track | Raw: 1-bit repair near the boundary | Address used if both bounds agree | To the previous track |
| redumper | Dump the whole disc, then analyze | `001b` raw P-W | 1 in the dump | Rebuilt from neighbors | Whole-disc shift by majority | Decided by the P channel |
| Ours (`src/pregap.c`) | Bounds, backtrack, walk | `010b` formatted Q | Up to 5, then 200 | Counted, sector skipped | Placed by its own address | To the previous track |

### cdrdao

- [code] `read-toc` analyzes each track with `GenericMMC::analyzeTrack()`. If the drive can read
  sub-channel with audio, it scans linearly; otherwise it binary-searches
  (`dao/GenericMMC.cc:1652-1667`). `--fast-toc` skips both (`dao/CdrDriver.cc:2272`).
- [code] The scan (`CdrDriver::analyzeTrackScan()`, `dao/CdrDriver.cc:2449-2560`) reads every
  sector of the track in batches. Each frame must pass `checkCrc() && checkConsistency()`
  (`:2489`). The first mode-1 frame naming the next track with index 0 sets the pregap from that
  frame's own absolute time: `*pregap = endLba - (atime.lba() - 150)` (`:2522`). One frame decides.
  Frames failing the CRC are counted and ignored, with no retry.
- [code] The comment above that line explains why it uses the absolute time and not the relative
  time. Relative time "would count one frame too many if the CD counts the pre-gap down to
  00:00:00 instead of 00:00:01" (`:2513-2519`). [doc] The ChangeLog for 1.2.3 (2009-10-05) says
  "Fixed old pregap length off-by-one error, see bug #604751".
- [code] Read mode (`GenericMMC::readSubChannels()`, `dao/GenericMMC.cc:1684-1800`): READ CD with
  byte 10 = `0x01`, raw P-W, if the drive passed the raw probe (`:1712`); otherwise `0x02`, 16-byte
  PQ (`:1719`). In PQ mode the CRC is not checked: "the CRC of the sub-channel data is usually
  invalid -> mark the sub-channel object that it should not try to verify the CRC"
  (`:1790-1792`). A failed SCSI command is resent up to 5 times (`:1687`).
- [code] The PQ probe (`readCdTest()`) counts a frame as good when its absolute address is within
  20 sectors of the sector asked for (`dao/GenericMMC.cc:2491`, `:2504`). The probe itself
  expects Q frames that do not answer for the exact sector.
- [code] The binary search (`CdrDriver::findIndex()`, `dao/CdrDriver.cc:2410-2447`) gets each Q
  frame with PLAY AUDIO of one block, waits, then READ SUB-CHANNEL
  (`GenericMMC::getTrackIndex()`, `dao/GenericMMC.cc:2316-2380`). No CRC is available on that path.
- [doc] `README.md:120`: `generic-mmc` "scans linearly the Q sub-channel ... This method is very
  accurate". `README.md:127`: the binary search "is usually not very reliable". Driver option
  `0x1` forces 16-byte PQ (`README.md:123`), `0x2` says it is BCD (`:124`).

### whipper and morituri

- [code] whipper runs `cdrdao read-toc` once without `--fast-toc` for the table
  (`whipper/common/program.py:126`, `whipper/program/cdrdao.py:98-100`). It warns that cdrdao
  before 1.2.3 "has a pre-gap length bug" (`whipper/common/program.py:104-107`). A track's pregap
  is index 1 minus index 0 from cdrdao's TOC (`whipper/image/table.py:129-139`). whipper has no
  sub-channel code of its own.
- [code] morituri does the same (`morituri/program/cdrdao.py:354`). It also caches the table by
  disc ID (`morituri/common/program.py:160-170`), so a later rip reuses the first rip's pregaps.

### XLD

- [code] `xld_cdda_read_pregap()` (`XLDCDDABackend.c:712-860`) starts 300 sectors (4 s) before the
  track start (`:746`). It reads 75 sectors per call (`:722`) through `DKIOCCDREAD` with
  `kCDSectorAreaUser | kCDSectorAreaSubChannelQ` (`:728`), up to the track start. Which READ CD
  sub-channel value macOS sends for that is not established.
- [code] A frame counts only with a non-zero CRC that matches (`:773`). The index is read from
  mode-1 frames only. A small state machine needs two index-0 frames in a row before it calls the
  stretch a pregap: "not a pregap" to "suspicious" to "pregap" (`:791`, `:794`). The length is
  counted by position read, not by the frame's address (`:854`).
- [code] On a CRC failure it re-reads the chunk from that sector up to 5 times (`:837`), then
  moves on. It gives up after 100 failures with no valid frame (`:831`). If CRC fails until the
  fields are re-encoded as BCD, it switches to non-BCD mode and starts again (`:801-826`).
- [inference] A frame answering for another sector is counted where it was read. A mode-2 or
  mode-3 frame on the first pregap sector does not start the count, so XLD's pregap would be one
  frame short there.
- [doc] Release notes mention pregap fixes for Plextor (2011-09-24, 2014-04-27) and Hitachi-LG
  drives, and "Improved pregap detection speed, especially on LG slim drives" (2015-12-14).

### CUERipper (CUETools)

- [code] `LocateLastSector()` (`CUETools.Ripper.SCSI/SCSIDrive.cs:336-460`) binary-searches. At
  each step it reads a 5-sector window from the middle sector minus 1 to plus 3 (`:343-345`), with
  one READ CD. `Device.ReadSubChannel()` sends READ CD with expected type CD-DA, no main channel
  and byte 10 = the mode, here 2, formatted Q (`Bwg.Scsi/Device.cs:2216-2222`).
- [code] A frame is skipped if its CRC is non-zero and wrong (`SCSIDrive.cs:409`); a zero CRC is
  accepted. Frames that are not mode 1 are skipped (`:411`). Each frame is placed at its own
  absolute address (`:423`). A frame outside the current bounds is ignored (`:437`).
- [code] If no window frame helps and the bounds are within 16 sectors, it returns the lower
  bound with no warning (`:452-456`). Otherwise it throws "gap detection failed" (`:459`).
- [code] The read-mode probe accepts a frame within 8 sectors of the sector asked for
  (`SCSIDrive.cs:543`). If READ CD with Q fails, it falls back to a one-sector read followed by
  READ SUB-CHANNEL `42h` (`:358-389`).
- [inference] With a mode-2 or mode-3 frame on the first pregap sector, the search narrows to
  that sector, then the 16-sector fallback returns the lower bound. Track N's last sector is then
  the one before that frame, which gives the frame to track N+1: one frame more pregap than cdrdao
  or XLD would give.

### dBpoweramp

- [forum] Its developer (spoon), 2008: "dBpoweramp will not detect the gaps (they are prepended to
  tracks)." In 2020: "Gaps are appended to the end of the track."
- [forum] A "Gap (Pre-Track)" column, asked about in 2018 for R16.4, detects gaps for display and
  for a DSP effect that removes them. Spoon, 2018: "There is a DSP effect which uses those values
  to remove the pre track silences." And: "It is only shown if you have a column set to show gaps,
  if you go for the default columns then it will not need to detect the gaps."
- [doc] dBpoweramp's version history page: "CD Ripper: added 'Gap (Pre-Track)' column" (quotation
  marks changed), and "Fixed pregap detection feature of CD Ripper not working on recent Mac OS
  versions" (R17.8 beta).
- Not established: what dBpoweramp reads, how often, or how it handles bad frames.

### cyanrip upstream

- [code] `master` takes each track's pregap from `cdio_get_track_pregap_lsn()`
  (`src/cyanrip_main.c:313`). In libcdio only the image drivers implement it
  (`lib/driver/image/bincue.c:1361`, `image/cdrdao.c:1356`, `image/nrg.c:1525`). Every other
  driver returns `CDIO_INVALID_LBA` (`lib/driver/track.c:329-341`). So upstream `master` reports no
  pregap for a physical disc.
- [doc] Upstream pull request 115 (UltraFuzzy), the source of our `src/pregap.c`, was closed on
  2026-10-22 in favor of pull request 153 (nicosp), which is open.
- [doc] Pull request 153's description says its search finds "index 0 sectors between two track
  starts, confirming each bound with a second read." It "Reads raw P-W where the drive supports
  it: a 10-sector probe on first use picks raw P-W if the drive accepts it and most frames carry a
  valid CRC". And: "In formatted mode, some drives silently return the previous sector's frame,
  with a valid CRC, in place of a damaged one. That made pregaps come out a frame short and vary
  between rips." It was tested on one drive, an Optiarc AD-7740H, with 12 discs. "Every pregap
  matches `cdrdao read-toc`", except where cdrdao drops a frame for a CRC error.
- [code] In pull request 153, a bound moves only after a second read agrees. The sector below a
  left bound must also be the previous track's (`src/pregap.c:140`). A right bound moves only
  "once a second new-track sector above the candidate agrees" (`:180`). A mode-2 or mode-3 frame
  right after the left bound is taken as the previous track's: "assume a pregap doesn't start on
  one" (`:205`).
- [code] It uses the frames' absolute time "if the frames on both bounds agree"
  (`src/pregap.c:280-287`). With at most 8 sectors left between the bounds, it re-reads them raw.
  It repairs a single-bit error by trying every bit against the CRC (`src/subq_read.c:261`). It
  accepts a frame only if its address is exactly the sector asked for (`src/pregap.c:234`). In
  formatted mode, a frame without a CRC is accepted if its address is within 20 sectors, "same as
  cdrdao" (`src/subq_read.c:29`). The header says formatted Q "may be the drive's last good frame
  and may lack the CRC" (`src/subq_read.h:32`).
- [forum] On the same pull request, UltraFuzzy said the 200-retry pass came from "informal testing
  where I observed a first successful read after ~180 attempts". He weighed it against "the risk
  of generating a spurious CRC validation from a hash collision".

### redumper and DiscImageCreator

They are disc preservation dumpers, not rippers, but they read the sub-channel most thoroughly.

- [code] redumper reads every sector with raw P-W (`READ_CD_SubChannel::RAW`,
  `cd/cd_common.ixx:477`). Its drive table lists "PIONEER BD-RW BDR-209D" firmware 1.10: read
  offset +667, READ CD `BEh`, sector order `DATA_SUB`, meaning data plus sub-channel and no C2
  (`drive.ixx:239`).
- [code] When it loads the dump, it makes a histogram of each valid mode-1 frame's address minus
  the sector it was read at. If the most common difference is not 0, it shifts the whole Q stream
  and logs "warning: shifting subchannel data" (`cd/cd_common.ixx:232-275`).
- [code] A frame failing its CRC is rebuilt. Candidates are generated forward from the last valid
  frame and backward from the next one, plus MCN and ISRC candidates. The one with the fewest
  differing bits replaces it (`cd/cd_common.ixx:301-430`). The code notes that the "point index
  0->1 transition sometimes adds an extra zero MSF value with point index 0" (`:369`, `:395`).
- [code] The P channel is decided by majority over its 96 bits (`cd/cd_common.ixx:294`). Where
  MCN or ISRC frames leave the track boundary imprecise, redumper places it at the P transition:
  "P is always 1 sector delayed" (`cd/toc.ixx:298-306`).
- [code] During the dump, a change in that difference is logged as "subcode desync (shift: …)"
  (`cd/cd_dump.ixx:142`). On the first pass, after more than 5 consecutive Q errors, it flushes
  the drive's cache. The comment says "PLEXTOR: some drives byte desync on subchannel after mass
  C2 errors" (`cd/cd_dump.ixx:164-169`, called at `:447-448`).
- [code] DiscImageCreator selects raw P-W before its CD dump (`CDFLAG::_READ_CD::Raw`,
  `DiscImageCreator/DiscImageCreator.cpp:224`). It checks each frame against the previous and
  next ones. For a lone mode-2, mode-3 or mode-6 frame between mode-1 frames, it tests whether the
  ADR nibble itself is corrupt: "assume that adr is incorrect" (`DiscImageCreator/fix.cpp:465`).

## 3. Drive behavior

**Q frames that answer for another sector.**

- [doc] MMC-3 r10g, §5.22.2, READ SUB-CHANNEL current position: "In other cases, for instance
  after a READ command, the Logical Unit may either report position data for the last sector
  processed for that operation or may report position data from the sector at the current read
  head position." The standard does not tie a READ SUB-CHANNEL answer to the sector last read.
- [doc] Pull request 153: in formatted mode, some drives return "the previous sector's frame, with
  a valid CRC, in place of a damaged one" (quoted above).
- [code] Tolerances in code: cdrdao's probe 20 sectors, CUETools' probe 8, and pull request 153's
  check of frames without a CRC 20 (section 2).
- [forum] redumper's author on issue 179 (2024): "If we see desync -1 at the disc start and it
  doesn't go back to desync 0 it means that whole subchannel on this disc is shifted by 1 sector."
  Redump's wiki records desyncs of up to 50 sectors on protected discs.
- [forum] Redump forum, 2025: DiscImageCreator and redumper split two tracks of one disc with
  different pregap lengths "due to the subcode desync messages".
- [forum] libcdio-devel, 2008: raw P-W "allowed you get a better sync with the audio, whereas Q
  was not guaranteed to be sector-matched with the audio you're playing."
- [forum] Hydrogenaudio topic 91150 (2011): "I also saw a mention that the subcode data is
  sometimes offset from the audio data it corresponds to."

**Formatted Q versus raw P-W.**

- [doc] MMC-3 Table 151, READ CD sub-channel data selection: `000b` none; `001b` "RAW P-W
  Sub-channel data"; `010b` "Q data shall be transferred"; `100b` "R-W data", which "may" come
  "de-interleaved and error corrected". All but `000b` are optional.
- [doc] MMC-3 Table 152, formatted Q: bytes 10 and 11 are "CRC or 00h (CRC is optional)". Bit 7
  of byte 15 "may (optionally) contain the P Sub-channel value."
- [inference] "De-interleaved" applies to the R-W packs. In raw P-W, each of the 96 bytes carries
  one bit of every channel, so Q is bit 6 of each byte in raw order. cdrdao reads it that way
  (`dao/PWSubChannel96.cc:130-148`), and so do redumper and pull request 153
  (`src/subq_read.c:140`). No reader examined needs a de-interleaving step for Q.
- [forum] ImgBurn's author, 2009: some drives return "garbage" for READ SUB-CHANNEL's MCN and ISRC.
  libcdio marks READ SUB-CHANNEL "deprecated as of MMC-5" (`lib/driver/mmc/mmc_ll_cmds.c:505`).

**Binary instead of BCD.** cdrdao (option `0x2`, and a BCD-or-hex vote in its probe), XLD
(`nonBCD`), CUETools (`_qChannelInBCD`), pull request 153 and our search all handle drives that
return the Q fields as binary. [code]

**How rippers compensate.** Not found: a per-drive Q offset setting in cdrdao, EAC, XLD or
CUETools. Compensation is automatic: placing frames by their own address (cdrdao's scan, CUETools,
pull request 153, ours), or a whole-disc shift computed from the data (redumper). [code]

## 4. External references for pregaps

None checks `INDEX 00` positions.

- **MusicBrainz** [doc]: a disc ID hashes the first and last track numbers, the lead-out offset
  and the "frame offsets" of each track from the TOC ("Disc ID Calculation"). Those are `INDEX 01`
  offsets. MusicBrainz stores a "pregap (track 0)" track for hidden audio before track 1, but no
  per-track `INDEX 00`.
- **gnudb and freedb** [doc]: the disc ID uses each track's TOC start offset and the disc length.
  Entries carry "# Track frame offsets", the starts "obtained from the table of contents".
- **AccurateRip** [code]: CUETools computes the disc ID from each track's `Start`, its `INDEX 01`
  (`CUETools.AccurateRip/AccurateRip.cs:1297-1314`). A track's checksum runs from its `Start` to
  the next track's `Start` (`:415-417`). Track 1's pregap is held apart (`:232`).
- **CTDB** [code]: the TOC sent is each track's `Start` and the disc length
  (`CUETools.CDImage/CDImage.cs:511-518`), with no `INDEX 00`.
- **Effect on checksums.** With gaps appended to the previous track, every track runs from its
  `INDEX 01` to the next `INDEX 01`, so the pregap's length changes neither checksum. [inference
  from the code above] [forum] Hydrogenaudio topic 32516: "If you tell EAC to append gaps to the
  previous track ... the tracks will not be affected by a difference in gap length." [doc] XLD's
  2008 release notes say AccurateRip is "Not available when pregaps are excluded."
- **EAC logs and cue sheets** carry pregaps: a "Pre-gap length" line per track, and `INDEX 00` in
  the cue sheet. No public, searchable collection of them was found. One from the same drive
  model is not independent.
- **Redump** [doc]: it catalogs audio CDs with cue sheets from redumper or DiscImageCreator dumps,
  verified by a second dump (wiki.redump.info, "Audio CD Guide"). That would be an independent
  `INDEX 00` source for a disc it holds. Whether it holds the reference disc is not established,
  and its listed audio CDs are mostly game soundtracks.

## 5. What a reliable method looks like

Each element below is used by at least one tool and cited above.

- **Read raw P-W (`001b`) where the drive supports it.** The CRC is then the disc's, and a
  damaged frame shows as a failed CRC, not as a substitute (pull request 153's description). The
  P channel comes with it. Used by cdrdao by default, redumper and pull request 153.
- **Read runs of consecutive sectors.** cdrdao scans whole tracks, XLD reads 75 sectors per
  command, CUETools 5 and redumper the whole disc. Pull request 153, like ours, reads one sector
  per command. Whether this changes what the BDR-209D returns is not established.
- **Place every mode-1 frame by its own absolute address,** as cdrdao's scan, CUETools and pull
  request 153 do, or correct a whole-disc shift, as redumper does. cdrdao's and CUETools' probes
  accept a read mode whose frames land within 20 and 8 sectors of the sector asked for.
- **Require agreement before moving a bound.** XLD needs two index-0 frames in a row; pull request
  153 needs a second agreeing sector. EAC's Accurate and Secure modes repeat the reading. Repeated
  reads that agree still prove only that the drive answers the same way each time.
- **Rebuild or repair frames from neighbors, and say so.** redumper picks the closest of the
  generated candidates; pull request 153 repairs one bit and accepts the frame only if its address
  is the sector asked for.
- **Use the P channel only as a labeled secondary observation.** MMC-3 §4.2.3.1: "During a
  transition area, the value for P is 1." But redumper treats P as "always 1 sector delayed"
  (`cd/toc.ixx:303`). Redump forum posts say "P channel tends to be off by 1 sector always" and,
  of one disc, "P normally indicates the track start, but in this case it started 47 frames
  early." P can break a tie; it cannot decide a boundary.
- **Do not infer the pregap's start from relative time.** MMC-3 §4.2.3.4.1: during the pregap
  "the time decreases". It counts toward `INDEX 01`, which the TOC already gives, and discs
  differ on whether it ends at `00:00:00` or `00:00:01` (cdrdao bug 604751; redumper
  `cd/cd_common.ixx:369`). A Redump forum post: "don't assume the pregap length based on the
  countdown start". Pull request 153 used the countdown only to confirm frames it had observed.
- **Lower read speed.** Only one report bears on it: the 2010 blog test, where EAC method A with
  Secure was stable across speeds and B was not. Not established as a general remedy.

### Mode-2 and mode-3 frames on a boundary

- [doc] MMC-3 §4.2.3.4: mode-1 Q "occupies at least 9 out of 10 successive CD frames". Mode-2 Q
  (MCN), if present, "shall occupy 1 out of each 100 successive frames". Mode-3 Q (ISRC), if
  present, "occupies at least 1 out of 100". Mode-2 and mode-3 frames carry only the frame number
  (`AFRAME`) of their position, with no track or index. "The ISRC may only change immediately
  after the Track Number (TNO) has been changed."
- [doc] MMC-3 §5.22.2, note on READ SUB-CHANNEL: when the current frame is MCN or ISRC, "the
  track, index, and address fields should be extrapolated from the previous sector." A drive that
  does this reports a mode-2 or mode-3 first pregap sector as the previous track's.
- So such a frame on the first pregap sector can cause an off-by-one. Each tool resolves it by
  rule, not by observation:

| Tool | Where the frame goes | Basis |
|---|---|---|
| cdrdao scan | Previous track; pregap starts at the first mode-1 index-0 frame | [inference] `dao/CdrDriver.cc:2491-2522` |
| XLD | Previous track; the count starts at the first mode-1 index-0 frame | [inference] `XLDCDDABackend.c:776-796` |
| CUETools | Next track, through the 16-sector fallback | [inference] `SCSIDrive.cs:411`, `:452-456` |
| Pull request 153 | Previous track: "assume a pregap doesn't start on one" | [code] `src/pregap.c:205` |
| Ours | Previous track, if its frame number lines up with `left_bound + 1` | [code] `src/pregap.c` `pregap_observe()` |
| redumper | Where the P channel changes, taken as 1 sector late | [code] `cd/toc.ixx:298-306` |
| EAC | Not established | — |

This rule difference alone can make two tools disagree by one frame on a perfect read.

## How `src/pregap.c` compares

Our search and pull request 153 descend from the same pull request 115, so they share the
bounds, the 150-sector backtrack and the walk. The differences from the best practice above:

1. **Read mode.** We request formatted Q only: `subchannel_selection = 2` in
   `read_audio_subq_sectors_mmc()`. We have no raw P-W path, no READ SUB-CHANNEL path, and no P
   channel. Pull request 153 probes for raw P-W; cdrdao prefers it; redumper uses nothing else. On
   a drive that substitutes the last good frame, formatted Q can never return a frame of the
   damaged sector itself. That is consistent with the `.27` record for track 9
   (`docs/KNOWN-ISSUES.md`): every sector asked gave a frame passing its CRC, 210 frames were
   another sector's, and LSN 145567 was left undecided. Raw P-W would return the sector's own
   frame, failing its CRC if it is damaged.
2. **One sector per command, at scattered addresses.** `read_audio_subq_sector()` asks for one
   block. cdrdao's scan, XLD, CUETools and redumper read runs; pull request 153 also reads one.
3. **One frame moves a bound.** `pregap_observe()` moves a bound on any frame that passes its CRC.
   XLD and pull request 153 need a second agreeing observation. With up to 200 retries per sector,
   the chance that a corrupt frame passes its CRC (1 in 65,536 per corrupt frame) adds up across
   reads. The author of pull request 115 named that risk.
4. **Retries can hit the drive's cache.** The cache defeat between retries is commented out
   (`overflow_device_read_cache()`, in `read_audio_subq_sector_with_retries()`). If the drive
   serves formatted Q for a re-read from its cache, 200 retries can return the same substitute
   frame 200 times. Not established for the BDR-209D. On its first pass, redumper flushes the
   cache after more than 5 consecutive Q errors, on any drive; its comment names Plextor.
5. **No repair or rebuild.** We count a frame failing its CRC and skip the sector. redumper
   rebuilds it from neighbors; pull request 153 repairs one bit in raw mode.
6. **A zero CRC is rejected.** That is right for raw P-W. In formatted Q the CRC is optional
   (MMC-3 Table 152), and CUETools and pull request 153 accept a CRC-less frame by its position.
   It does not matter on the BDR-209D, whose frames carry CRCs, as our CRC-failure counts show.
7. **Where we already match or exceed the others.** We place mode-1 frames by their own address,
   as cdrdao's scan, CUETools and pull request 153 do. We track the drive's shift. We print an
   undecided sector as undecided: CUETools silently returns the lower bound within 16 sectors,
   cdrdao takes the first frame it accepts, and XLD the first two in a row.

## Options for us

Every option that changes drive I/O needs hardware verification on the BDR-209D, and touches the
`CLAUDE.md` rig-table row for two-search `Pregap source:`. A new log line or wording is handshake
material and needs a round. A green suite shows none of this works on a drive.

| Option | What it buys | Cost | Limits |
|---|---|---|---|
| A. One rig observation: read LSN 145560 to 145575 in raw P-W (`001b`) and formatted Q (`010b`), several passes with a cache defeat between them; record ADR, track, index, absolute time, CRC result and P per read | Settles which mechanism holds: a substitute frame, a damaged frame, or a mode-2/3 frame at 145567 | A small probe tool (not in the rip path) and rig time; no seam change | Shows what this drive returns, not the disc's truth; if 145567's Q is unreadable on every pass, it stays unknown |
| B. Run `cdrdao read-toc` and redumper on the rig, on the reference disc | Two independent implementations, both preferring raw P-W, to compare with 94 and 95 | Operator's time; both are other programs' claims, to be cited as theirs | Same drive; if the disc's frame is damaged, they apply their own rules (section 5) |
| C. Raw P-W read mode with a probe and fallback, as in pull request 153 | Frames are the disc's own; damaged frames show as CRC failures; P comes free | About 100 to 150 lines in `src/pregap.c`, tests in `tests/subq.c` with 96-byte frames, a log line saying which mode ran (round needed) | More frames fail their CRC, so more `unknown` unless repaired; raw support varies by drive (redumper's table lists the BDR-209D, firmware 1.10, with sub-channel reads, `DATA_SUB`) |
| D. Confirmation rule: a bound moves only on two agreeing observations | Removes single-frame decisions and CRC-collision risk | Small; more reads per search | Turns some 94s or 95s into undecided; cannot fix a drive that substitutes the same frame every time |
| E. Read runs of sectors (for example 16 per READ CD) and place each frame by its address | Matches cdrdao, XLD, CUETools and redumper; may avoid seek-related substitution | Small: block count and buffer | Effect on the BDR-209D not established |
| F. Cache defeat between retries of one sector | Makes a retry a new read, not a cached answer | Reuse what `src/cache_probe.c` knows; more time per retry | Effect not established; the cache model is itself a model |
| G. P channel as a secondary observation, printed with its source | A labeled tie-breaker for a mode-2/3 boundary | Needs option C, or formatted Q byte 15 if the drive sets it; a log field (round needed) | P is often a sector late and sometimes far off; never a decider |
| H. Keep "94 or 95 (undecided)" and add why the sector is undecided: no frame of its own, a failed CRC, or a mode-2/3 frame | Says exactly what was observed; no external reference exists to do better | Wording and a round | Does not resolve the value |
| I. A second drive model with good raw P-W (one in redumper's table) | An observation through different firmware | Hardware; the owner's decision | Different drives can disagree too (Hydrogenaudio reports above) |

A and B decide which of C to G are worth building, so they come first. H is the right report for
any sector the reads leave undecided, whatever is built.
