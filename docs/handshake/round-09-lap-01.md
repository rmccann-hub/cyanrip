## D. Log-format delta — one line, and it has never reached an archived rip

**`Cache probe:`, and nothing else.** Said out loud rather than left to
inference.

`-x` ran on real hardware for the first time in this project's existence on
2026-08-10 — no disc-image fixture will execute it, by design — and produced
two defects and one correction in a single evening.

**What `ddf7ac3` printed:**

```
Cache probe:    32 sectors measured (73.5 KiB, uncached read 364.3 ms)
```

**What is actually true**, from `cd-paranoia -A` on the same drive and disc:

```
Approximate random access cache size: 137 sector(s)
Drive readahead past read cursor:     119 sector(s)
Backseek flushes the cache as expected
```

So that line was **wrong by a factor of four**, in a line destined for an
archival record. Three separate faults produced it:

1. The doubling search can only return a power of two, so its result is a
   bracket, never a measurement. `measured` claimed a precision the method
   cannot deliver — the `Cache defeat:` → `Cache model:` lesson one level in.
2. The search stops for **four** reasons and all four printed the same
   sentence. "The cache ran out at 64" and "the read at 64 failed" are
   different claims about a drive.
3. **The read at 64 sectors failed because of our own transfer size.** 64
   sectors is 150,528 bytes in one command; an `sr` device's `max_sectors_kb`
   is commonly 128 KiB. The ceiling was ours, and the probe could never have
   reached 137 no matter what the drive cached.

(1) and (2) are fixed in `1f00653`; (3) in `8a045de`, which now issues the run
as 25-sector commands — 58,800 bytes, under even a 64 KiB limit. **The wording
fix did not make the probe correct. It made it stop claiming what it had not
established**, which is its job, and it did that on its first hardware run.

All nine wordings are pinned by `tests/cacheprobe.c`. The wording is unchanged
from what round 8 lap 1 described; what changes is which one a real drive
produces, and the numbers in it.

### D-pred. A falsifiable prediction — please check it

On the rig's PIONEER BD-RW BDR-209D with the same disc, beta.2 should report:

```
Cache probe:    128 to 255 sectors (...)
```

A 137-sector cache means a hit at 128 and a miss at 256, and `[128, 256)`
contains 137. **Anything else falsifies the fix**, and we would rather hear it
than have it pass unexamined: another `read failed while growing the run` means
the chunk is still too large; a bracket not containing 137 means our method and
cd-paranoia disagree about what a cache boundary is, and neither number can be
trusted; `search ceiling reached` would contradict cd-paranoia by an order of
magnitude.

**This is not a close condition.** Its failure is a round 10 matter unless it
shows beta.2 is unsafe, which a bounded, self-disclosing line cannot be.
