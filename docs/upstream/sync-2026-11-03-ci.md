## 2. How the merge is resolved

- **`.github/workflows/main.yml` stays deleted.** Ours is `ci.yml`, moved there
  in `86561ff` so that `master`'s workflow cannot shadow it; taking upstream's
  back would run its jobs, with actions named by tag rather than by commit, on
  every push here.
- **`.github/mingw-build.sh` stays ours.** Ours pins each library to a git
  commit, and LAME's tarball to its SHA-256, and caches what it builds;
  upstream's builds from moving git heads. Its one new thing, chromaprint, is
  not taken: our `mingw-release` job attaches the Windows binary to a GitHub
  release, and the fork has made none (`gh api .../releases` returns an empty
  list, 2026-11-03), while Platterpus runs on Linux only (`DEPENDENCY-PLAN.md`
  §2). It would buy build time and a dependency for no user.
- **`.github/static-build.sh` is not added.** No workflow of ours calls it, and
  a build script in the tree that nothing runs reads as one that something
  does. (The dependency map reads only `.github/workflows/*.yml` and
  `mingw-build.sh`, `tools/gen-dependency-map.py:277` and `:310`, so it would
  not have listed it either.)

So the merge commit's tree is `eb0f1ae`'s. What changes is the merge base,
`648b1dd` from `7dbe56a`, so the next sync's delta starts there.

## 5. What it suggests, not taken here

**Upstream now ships a static Linux binary with each release.** An end user of
ours gets cyanrip by building it inside Platterpus's Fedora container, from
Fedora's packages, without libqrencode or libchromaprint
(`DEPENDENCY-PLAN.md` §2). A static binary of our fork, built by our CI and
named by `release-manifest.json` with its SHA-256, would let Platterpus's
installer download what CI tested instead of building something no CI job
builds, with QR codes and AcoustID in it. It would also change how every
user gets the program, which makes it handshake material and the installer
Platterpus's; it needs the owner's word and a round, and is listed in
`DEPENDENCY-PLAN.md` §5.
