## 1. `[CORRECTION]` A finding I reported earlier was wrong

**I told the operator upstream had "reintroduced the bare `Peak:` label we
renamed away from." That is not what shipped.** The correction, and the reason
it happened, matter more than the original claim:

```
b227408 (intermediate)  +  cyanrip_log(ctx, 0, "    Peak:        %.6f\n", ...)
61679ba, 3b75740 "Address PR comments"  -> renamed
master (merged state)      cyanrip_log(ctx, 0, "    Sample peak: %.6f\n", ...)
```

I read the commit that *introduced* the line instead of the merged tree. Two
later commits in the same series renamed it, so the label I quoted **never
existed in any released upstream build.**

> **The rule this earns: compare merged trees, never individual commits in a
> series.** A PR branch renames things after the commit that introduces them,
> and a diff hunk read in isolation reports a label nobody will ever see.
> `tools/upstream-delta.py` uses `git show <ref>:<path>` for exactly this
> reason, and its docstring records the incident.

The real collision is narrower than I first said, and still real — §3.

## 3. The log-text collision: `Sample peak:` vs `Sample peak level:`

Both binaries, ripping the same fixture, at **track** level:

```
upstream:   Sample peak: 1.000000
ours:       Sample peak level: 100.0% (0.0 dBFS)
            True peak level:   0.0 dBFS
```

**A parser matching the prefix `Sample peak` matches both.** That is the
collision, and it is worth being precise about why it is ours to care about:
our own source comment at `cyanrip_log.c:352` says we chose `Sample peak level`
so it *"cannot be confused with libavfilter's own `  Sample peak:` /
`  True peak:`"*. Upstream has now introduced a **cyanrip-emitted** line with
exactly that libavfilter spelling, at track level. The confusion our naming was
designed to avoid now exists in a new place.

### The interesting part: we both independently added the same measurement

| | ours | upstream |
|---|---|---|
| field | `direct_sample_peak` | `sample_peak_rel_amp` |
| how | direct max\|sample\| scan | direct max\|sample\| scan |
| units | percent + dBFS | relative amplitude 0.0–1.0 |
| printed | **only on disagreement** with ebur128's figure | **always** |

**Convergent evolution.** We added a direct scan as a *cross-check* against
ebur128's `ebu_sample_peak`, and print `Sample peak disagreement:` only when the
two differ — deliberately, because two always-present numbers for one fact
invite a consumer to pick one, and whichever it picks will occasionally be the
wrong one silently. Upstream added the same scan and prints it unconditionally
as a value.

Neither is wrong. They answer different questions: ours asks *"do two
measurements of the same frames agree?"*, theirs asks *"what was the peak?"*.
A sync has to decide whether to carry both, and if so how to name them so a
consumer can tell which is which.

## 4. MusicBrainz selection changed — and it is downstream's call

```
ae5b996  Prefer track title over recording title          (PR #158)
4f28cf0  Also prefer track artist credit over recording artist credit
```

A MusicBrainz *recording* is the shared audio entity; a *track* is that
recording as it appears on one specific release. Preferring the track title and
artist means the log, the filenames and the tags read as **that disc** reads,
rather than as the shared recording is named.

**Platterpus already ruled on this and the ruling now applies.** Asked about
PR #158 while it was open, they said: *wait for upstream; if it merges, we take
it with your next sync, and it is handshake material because it moves log text.*
It has merged. So this is wanted, not merely available — but it is theirs to
time, because MusicBrainz selection sits on their side of the ownership split.

**It is invisible to our test suite.** Every fixture rips with `-N`, so no
MusicBrainz lookup happens and no test would notice this change either way.
Any adoption needs a deliberate check against a real lookup.

## 5. QR codes: stdout only, but not nothing

`f2848bd` adds `src/qrcode.c`, printing the MusicBrainz submission URL as a QR
code. `[MEASURED]` from the source: it emits via `fputs(buf.str, stdout)` and
**never through `cyanrip_log()`**, so it cannot reach a logfile.

Two things still make it observable:

- it writes **ANSI colour escapes** (`\033[38;5;…m`) to stdout, and Platterpus
  captures our stdout as a mitigation for messages that never reach a logfile;
- it adds `libqrencode >= 4.0` as an optional dependency. `required: false`, so
  a build without it prints *"libqrencode not found, MusicBrainz URLs won't be
  printed as QR codes"* and carries on.

Optional means it degrades rather than breaks — but a dependency that changes
what a consumer must install to reproduce our output is handshake material by
the *"could the other side notice?"* test.

## 7. What we would have to fix, if we synced

Ordered by how much they cost, not by how much they matter:

1. **Rename or reconcile the peak lines.** Carrying upstream's
   `Sample peak:` beside our `Sample peak level:` gives a prefix collision in a
   log Platterpus parses. Options: take theirs and drop ours, keep ours and skip
   theirs, or keep both under names that discriminate. All three are log-text
   changes and therefore a handshake round.
2. **Regenerate every derived artifact.** `PROVIDER-CONTRACT.md`,
   `docs/golden-reference.log` and its diagnostics JSON all move — the contract
   because a new `cyanrip_log()` call site appears, the reference because the
   version string and the track block both change.
3. **Version bump to `0.9.4-rc2+platterpus.7`,** which is a release, which
   needs a closed round first.
4. **Decide on `libqrencode`** — carry the feature, or carry the code and leave
   the dependency unlisted.
5. **Re-run the four-configuration CI matrix**, including sanitizers. Upstream's
   new peak scan is a tight loop over raw sample bytes with an `abs()` on
   `int16_t`; it is exactly the shape ASAN and UBSAN exist for, and it has never
   been run under either.

## 8. What we would have to *not* lose

`tools/upstream-delta.py` lists **52 log lines we emit that upstream does not**.
That is the fork, and a careless merge is how it goes missing. The ones most
easily lost, because upstream touches the same functions:

- `C2 errors:      %_` — ours; upstream's is `C2 errors:      %_ by drive`,
  which we reworded deliberately
- `Handshake:` and `Consumer:`, with their qualifier lines
- `Cache model:` / `Cache probe:` — including the naming decision that
  `Cache defeat:` asserted something we never measured
- `Sample peak disagreement:` — §3
- `Pregap LSN: unknown (sub-channel unreadable)` and
  `unknown (sub-channel CRC mismatches)`. **Upstream has two states here and we
  have four**: they distinguish a value from `none`; we additionally
  distinguish two ways of *not knowing*. Collapsing ours into theirs would turn
  an absence of evidence into evidence of absence, on the field a reader would
  use to call a disc clean.

## 9. Recommendation

**Do not sync yet, and the reason is sequencing rather than risk.** The sync is
a release, a release needs a closed round, and the round it belongs to is the
one that has not opened — round 12, whose subject was going to be the manifest
schema and now has a version bump and a log collision in it too.

`master` staying current is what makes this analysis possible at all, and it
costs nothing: it is the mirror, it never merges into the fork, and no consumer
reference resolves through it.
