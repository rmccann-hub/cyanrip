# Steward push

Read this before pushing to a pull request's branch here: the suite run that must pass first,
generated files, commit subjects, merging the base in, and the pull request's own text.

It covers what goes up and how. Reading CI is `steward-checks`'s, fixing a red job
`steward-failures`'s, and the merge `steward-merge`'s. The rules themselves are `CLAUDE.md`'s;
this module is the order to apply them in.

## Rules

1. **Push only the branch the session is assigned, or one the owner named,** and only to open
   or update its pull request into `platterpus-fork`. A branch whose pull request merged is finished: restart the branch
   from `platterpus-fork` for new work (`steward-merge`).
2. **Run the full suite on the commit you will push, so that its result counts:**

   ```sh
   git fetch origin master                      # Settled facts reads upstream's master
   ninja -C build
   rm -f build/meson-logs/testlog.txt
   ps -eo pid,args | awk '$2=="/usr/bin/python3" && $3=="/usr/bin/meson" && $4=="test"'
   meson test -C build --print-errorlogs        # in the background, editing nothing
   ```

   The `ps` line must print nothing: two runs on one build directory write a log that is
   neither run. It passes when meson exits 0, its summary says `Fail: 0`, and the log holds
   exactly one `Log of Meson test suite run` header (`CLAUDE.md`, *Build and test*). Edit
   nothing in the tree until it ends. A fix pushed for CI meets the same rule.
3. **Read what the suite skipped,** and name in the pull request any test of its own that did
   not run here or will not run in CI (`steward-checks`).
4. **Regenerate what is derived; never hand-edit it.** After a change to a `cyanrip_log()` call
   site or the option table, `PROVIDER-CONTRACT.md`; after a dependency, a subprocess call, a
   URL or a workflow, the dependency map; after a lap or a log line, the golden reference
   (`CLAUDE.md`). Commit the regenerated file on its own, after the commit that made it stale,
   with a Changelog sentence naming both: **generated by `<commit>`** and **committed in the
   commit carrying this sentence**, the SHA on the same line. Never `--amend` it in: the
   commit it names would become unreachable.
5. **Check the subjects before pushing:** `python3 tools/check-commit-subjects.py
   origin/platterpus-fork HEAD`. Plain, imperative, at most 72 characters, capitalised, no full
   stop. CI runs the same check over the pull request's range, and a pushed subject can only be
   fixed by rewriting history.
6. **Stage files by name,** never `git add -A`: the tree holds build output, scratch files and
   other sessions' work. One change per commit, each green on its own, and a new test registered
   in `tests/meson.build` in the commit that adds it.
7. **End each commit message with the attribution lines** the session gives, and name no model
   in a commit, pull request or comment.
8. **Bring the base in by merging it,** never by rebasing a pushed branch: `git fetch origin
   platterpus-fork && git merge origin/platterpus-fork`. Resolve each conflict by reading both
   sides; if both changed the same logic and one would lose behaviour, ask. Then regenerate
   every derived file the merge touched, and run the suite.
9. **Push with `git push -u origin <branch>`,** and retry only a network failure, up to four
   times, waiting 2, 4, 8 and 16 seconds.
10. **Write the pull request so a reader can act on it:** what each commit does, how it was
    proved (the suite's result at the head, each revert proof), what CI does not cover, and
    whether anything the other side reads changed. Upstream issues are written *upstream issue
    N*, never as a link to `cyanreg/cyanrip`, which would post a reference there. The body ends
    with the session's attribution lines; a comment ends with the Claude Code footer. The tone
    rule of `CLAUDE.md` holds, aimed at a side or a session, never a person.
11. **Answer every review comment** on a pull request you opened: fix a small, local ask and
    push; reply with the reason when you don't. A bot's finding is a claim to verify, not an
    order.

## Mistakes

- **Pushing while the suite still runs, or on its first green line.** The summary and the log
  header are the result, not the progress lines.
- **Running a second suite on the same build directory.** Its log mixes both runs.
- **Folding a regenerated file into the commit that staled it.** The *generated by* sentence
  then names a commit that does not contain the source of what it generated.
- **Amending or rebasing a pushed commit.** Rewritten history breaks every citation of it; the
  rulesets refuse it on the protected branches, and nothing refuses it on a topic branch.
- **`git add -A`.** It stages whatever the tree holds, build output and scratch files
  included.
- **Linking upstream's tracker from a commit.** A commit carrying `cyanreg/cyanrip#167` and its
  URL posted a reference on upstream's issue.

## Audit

Severity uses the standard's status words.

| Check | What to look for | Severity | Fix |
|---|---|---|---|
| Suite before push | exit 0, `Fail: 0` and one header, at the pushed commit | fail | run it; push after |
| Derived files current | the generators' `--check` pass, each regeneration in its own commit with its sentence | fail | regenerate and commit on its own |
| Subjects | `tools/check-commit-subjects.py` passes over the branch's range | fail | reword before pushing |
| History | no force-push, no amend of a pushed commit | fail | none after the fact: report it |
| Coverage stated | the pull request names skipped tests and untouched hardware rows | warn | add the lines |
| Upstream references | no `cyanreg/cyanrip#N` and no link to its issues | fail | *upstream issue N* |

## Why

### The suite passes before every push

- **The advice:** the full suite, on the commit pushed, read by its summary and its log.
- **The reason:** the operator's rule, kept 2026-10-19 (`CLAUDE.md`). A failure the suite
  shows here in minutes costs a whole CI run to find there, and a red push must be fixed and
  pushed again.
- **What others do, and why:** many projects let CI be the gate and push freely; here CI's
  macOS runner is scarce, and a red push holds the pull request for another run.
- **What it costs:** the suite's run, minutes, with the tree untouched.
- **When to choose differently:** never; a push that changes only a comment still meets it.

### Regenerated files go on their own

- **The advice:** commit a regenerated artifact separately, naming the commit it came from.
- **The reason:** `CLAUDE.md`, *Branches, merges and tags*: an artifact needs two commits named,
  *generated by X, committed at Y*, and amending loses X.
- **What others do, and why:** many projects regenerate in the same commit; they don't cite the
  generating commit.
- **What it costs:** a commit and a Changelog sentence.
- **When to choose differently:** never here.
