# Steward failures

Read this when a job on a pull request here is red: the failures this CI has had, what each
was, its fix, and how to decide whether a failure is the pull request's at all.

It covers diagnosing and fixing. What green means is `steward-checks`'s, and the push that
carries a fix follows `steward-push`.

## Rules

1. **Read the failing job's log before forming a theory.** Find the first failing test, `N/M
   <name> FAIL` or `TIMEOUT`, and its error log, which `--print-errorlogs` prints; for a step
   that is not the suite, its own last lines. `gh api
   repos/rmccann-hub/cyanrip/actions/jobs/<job id>/logs` returns the whole log.
2. **Decide whose failure it is.** It is not the pull request's when the same job is red on
   `platterpus-fork`'s head, or when it names something the diff does not touch and reproduces
   on one re-run (`steward-checks`). Then comment once on the pull request with the job, why
   it isn't this one's, and the fix or that none exists yet. Anything else is the pull
   request's to root-cause and fix.
3. **Match it against the known failures below** before re-deriving it. A known failure has a
   known fix; a symptom that looks like one but differs in its numbers is a new failure.
4. **Reproduce before fixing** where this container can: the same test, built the way that row
   builds (`-Db_sanitize=thread -Db_lundef=false` for the TSan row, `-Ddeclare_released=true`
   for the released rows). A fix lands with a test that fails without it, proved by reverting
   the fix (`CLAUDE.md`, *Verifying your own work*).
5. **"Flake" is not a cause.** A failure that comes and goes has one: a race, a timeout too
   close to the runner's speed, a shared resource. Find it, as the TSan row's was found, rather
   than re-running until green.
6. **A timeout moves only with measurements beside it:** the time it took where it failed, where
   it passed, and why the new limit leaves room (fact `steward-settled-timeout`). The step *Where
   Settled facts spent its time*, in the suite and evidence jobs, prints that test's slowest rows.
7. **A new failure goes into the table below** in the pull request that fixes it: this file is
   owned here, and the next session reads it before re-deriving.

## Mistakes

- **Raising a timeout to get green.** It hides the slowdown that caused it, and the next
  slowdown fails at the new limit. Measure first; the comments in `tests/meson.build` show how.
- **Suppressing a TSan report broadly.** `ignore_noninstrumented_modules` dropped every access
  inside FFmpeg, the encoder side of the handoff the build exists to check. Name one function,
  with its proof.
- **Editing a generated file by hand.** Its check regenerates and compares, so a hand edit
  fails the next run, and the file stops saying what produced it.
- **Re-running until green.** A second failure is real (`SKILL.md`, rule 4).
- **Fixing the symptom in the wrong place.** The issues row failed because the clone's `master`
  was stale, not because the file was wrong; regenerating from the stale `master` made it fail
  in CI again.

## Audit

Severity uses the standard's status words.

| Check | What to look for | Severity | Fix |
|---|---|---|---|
| Log read | the first failing test and its error log named before any change | fail | read them |
| Ownership decided | a failure also red on the base branch said so in one comment | warn | compare the base's runs |
| Proof | the fix's test fails with the fix reverted | fail | revert-prove it |
| Timeout measured | a changed timeout has its measurements in the comment beside it | fail | measure, or put the old limit back |
| Table kept | a new failure, fixed, has its row here | warn | add it in the fixing pull request |

## Why

### Match the known failures first

- **The advice:** look the symptom up here before diagnosing it.
- **The reason:** on 2026-11-02 pull requests #75 and #76 met five of these in CI between
  them, and the local suite two more, and each was re-derived from its log because nothing
  recorded them outside the Changelog.
- **What others do, and why:** larger projects keep a flaky-test tracker; this repository's
  failures are few and each has a cause, so a table suffices.
- **What it costs:** keeping the table true, in the pull request that meets a new failure.
- **When to choose differently:** when the table outgrows this file's limit, split it by job.

### Name one function in a suppression

- **The advice:** a TSan suppression names the writing function, with the stack and how often
  it reproduced, and is proved by reverting it.
- **The reason:** the third entry in `tests/tsan.supp` matched 4 times in 120 rips of its
  scenario, with no warning left; without it, 2 of 120 failed on exactly that report.
- **What others do, and why:** many projects ignore uninstrumented libraries wholesale, trading
  coverage for quiet.
- **What it costs:** a reproduction, many runs long.
- **When to choose differently:** never here: the handoff to the encoders is what the row
  checks.
